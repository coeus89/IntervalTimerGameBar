# Architecture — system overview

## The shape of the thing

```
                       ┌───────────────────────────┐
                       │   IntervalTimer.Core       │   netstandard2.0
                       │                            │
                       │  IntervalTimerEngine       │  drift-free scheduler
                       │  TimerSettings / ISettings │  load/save POCO
                       │  SoundCatalog / SoundInfo  │  the 5 bundled tones
                       │  ISoundPlayer (interface)  │
                       └─────────▲───────────▲──────┘
                                 │           │
              ProjectReference   │           │   ProjectReference
                                 │           │
          ┌──────────────────────┴──┐   ┌────┴───────────────────────┐
          │  IntervalTimerOverlay   │   │  IntervalTimerWidget       │
          │  WinUI 3, unpackaged    │   │  classic UWP (.NET Native) │
          │                         │   │                            │
          │  MainWindow (overlay)   │   │  WidgetPage                 │
          │  JsonSettingsStore      │   │  AppDataSettingsStore      │
          │  MediaSoundPlayer       │   │  UwpSoundPlayer            │
          │  H.NotifyIcon (tray)    │   │  Microsoft.Gaming.XboxGameBar
          │  AppInstance (1 inst.)  │   │  App.OnActivated (protocol)│
          └─────────────────────────┘   └────────────────────────────┘
                    Start menu / .exe          Win+G  →  widget menu
```

Everything timing-related lives in **Core**. The two front ends are thin: they build the UI,
own an `IntervalTimerEngine`, subscribe to its two events, and provide platform
implementations of `ISettingsStore` and `ISoundPlayer`.

## Why two front ends

Xbox Game Bar widgets **must be UWP** — the SDK is activated through `App.OnActivated` with an
`ms-gamebarwidget:` protocol and needs a `CoreWindow`, neither of which exists in WinUI 3
([issue](https://github.com/microsoft/XboxGameBarSamples/issues/100)). And the widget can't be
a *modern* SDK-style UWP app either: `Microsoft.Gaming.XboxGameBar` ships a classic-UWP
`.winmd` that CsWinRT refuses to project in a `UseUwp` project (`error NETSDK1130`).

So the widget is **classic UWP / .NET Native** — the only configuration the Game Bar SDK
supports. Everything modern (and everything the average user actually wants) is the
**standalone WinUI 3 overlay**, which needs neither Game Bar nor pinning.

## Two solutions

| Solution | Projects | Build with |
| --- | --- | --- |
| `IntervalTimerWinUI.sln` | Core, Overlay, Tests | `dotnet` / VS 2026 / `build.ps1` |
| `IntervalTimerWidget.sln` | Core, Widget | **VS 2022** + UWP workload / `build-widget.ps1` |

The widget is kept out of the main solution because the .NET CLI can't build a classic
non-SDK UWP project, and VS 2026's project system can't load one. VS 2022 (17.x) with the
*Universal Windows Platform development* workload loads and builds it.

## The timing model

`IntervalTimerEngine` never counts down. It stores an absolute `DateTime _nextFireUtc` and,
on a 250 ms poll, compares it to `DateTime.UtcNow`:

- `now >= _nextFireUtc` once → raise `Elapsed`, advance `_nextFireUtc += _interval`.
- `now >= _nextFireUtc` by more than one interval (machine slept, widget was suspended) →
  raise `Elapsed` **once** with `Resynced = true` and realign `_nextFireUtc = now + _interval`
  so you don't get a burst of beeps.

This makes it immune to timer drift and to process suspension. `NextFireUtc` is public so the
widget can persist it and call `ResumeAt(...)` after Windows wakes it back up.

Events fire on a thread-pool thread; each front end marshals to its own UI dispatcher
(`DispatcherQueue.TryEnqueue` in WinUI 3, `CoreDispatcher.RunAsync` in UWP).

## Settings & persistence

`TimerSettings` is a plain object (`IntervalSeconds`, `SoundKey`, `Volume`, `AutoStart`) with
`Load(ISettingsStore)` / `Save(ISettingsStore)`. The store is per-app:

| App | `ISettingsStore` impl | Backing store |
| --- | --- | --- |
| Overlay | `JsonSettingsStore` | `%LOCALAPPDATA%\IntervalTimerOverlay\settings.json` |
| Widget | `AppDataSettingsStore` | `Windows.Storage.ApplicationData.Current.LocalSettings` |
| Tests | in-memory dictionary | — |

The overlay uses a JSON file specifically because it runs **unpackaged** — `ApplicationData`
throws without package identity.

## Sound

`SoundCatalog` is a static list of `SoundInfo { Key, DisplayName, FileName }`. Each app bundles
the same five `Assets/Sounds/*.wav` files (generated by `tools/gen_sounds.py`) and plays them
through `Windows.Media.Playback.MediaPlayer`:

- **Widget** (packaged): `MediaSource.CreateFromUri("ms-appx:///Assets/Sounds/beep.wav")`.
- **Overlay** (unpackaged): `MediaSource.CreateFromUri(new Uri(<baseDir>\Assets\Sounds\beep.wav))`
  — `ms-appx:` doesn't resolve without a package.

## Key decisions log

| Decision | Why |
| --- | --- |
| Shared `netstandard2.0` Core | The lowest common denominator UWP (.NET Native / C# 7.3) and modern .NET both consume. C# 7.3 / nullable-disable is enforced in `IntervalTimer.Core.csproj`. |
| Absolute-time engine, not a countdown | Drift-free; survives sleep and widget suspension. |
| Widget = classic UWP | Only config the Game Bar `.winmd` works in. Built by VS 2022 only. |
| Overlay on **.NET 10 + Windows App SDK 2.4** | Current LTS runtime; one modern stack. |
| Overlay = unpackaged | So it's a plain double-click `.exe` — no MSIX, no cert, no registration. |
| Overlay: no ReadyToRun | R2R triggers a CsWinRT `ComInterfaceEntry` `TypeLoadException` in self-contained publishes. Trimming is now safe (source-gen JSON) but stays opt-in. |
| Overlay `JsonSettingsStore` uses `System.Text.Json` **source generation** | Trim/AOT-safe; `SettingsJsonContext`. |
| Overlay drag via `GetCursorPos` | The window has no non-client area, so `InputNonClientPointerSource` caption regions don't apply. Screen coords avoid the feedback jitter that element-relative coords cause. |
| Single-instance in **`Program.Main`** (`DISABLE_XAML_GENERATED_MAIN`) | `AppInstance` redirection runs before the XAML runtime starts, so a redundant launch exits cleanly with no half-built `App` — no `Process.Kill()`. |
| Central package management | `Directory.Packages.props` at the repo root; `global.json` pins the SDK. The non-SDK widget opts out via nested `Directory.*.props`. |
